## 1. 目标与范围

Liang's Fishing Schedule 是一个手机优先的个人钓鱼网站：把潮汐、天气、风、浪、水温、河流流量汇总到一页，并给出未来 7 天每个钓点的推荐时段。打开网站要解决的问题只有一个：**这周哪天、几点、去哪个钓点。**

- **使用者**：Liang 和他的朋友。所有人可浏览，只有 Liang 可以编辑。
- **覆盖范围**：基督城附近。第一版两个钓点：New Brighton Pier、Southshore。
- **设计原则**：
  - 采集、评分、UI、记录四个模块互相独立，只通过约定的 JSON 和数据表通信，换掉任何一个不影响其他。
  - 后端逻辑全部用 Python，Liang 要能直接改数据处理和评分规则。
  - 技术栈尽可能简单，全部运行在免费额度内。

**第一版不做**：提醒通知、添加到主屏、多语言、禁渔规定、用户注册、评论。

**界面语言**：网站界面只用英文，不做语言切换。本文档里引用的界面文案是中文说明，实现时全部写成英文。

## 2. 页面结构

单页，手机优先，从上到下依次是：

1. **个人视频**：站名加 YouTube 嵌入视频。不自动播放，手机上高度不超过屏幕的 40%，保证下一块在首屏露出。
2. **今日结论**：每个钓点一张卡片，显示今天最好的时段和分数；没有合适时段就直接写“今天不推荐”。
3. **本周推荐**：未来 7 天的推荐时段列表，加一张标注钓点的地图。点开某个时段能看到评分理由。3 天以后的时段标为“低可信”。
4. **条件时间轴**：一张共用时间轴的图，叠放潮位曲线、风速与阵风、降雨概率、浪高，可切换钓点、左右滑动 7 天。图下方是明细：
   - 潮汐表：每天高低潮的时间和高度、日出日落、月相。
   - 水温曲线。
   - 天气概观：逐小时气温、天气图标、降雨概率。
   - 风：风速、阵风、风向，并标明相对岸线是离岸、向岸还是侧风。
5. **Waimakariri 流量**：默认折叠，用户点击后才加载并显示图表。
6. **Fishing record**：按时间倒序的记录列表，含照片、视频链接、当时的条件。编辑入口只在 Liang 登录后出现。
7. **页脚**：数据来源署名、各数据块的更新时间、免责说明。

通用要求：

- 单列布局，最小适配宽度 360px，图表支持手指滑动。
- 每个数据块显示“更新于 X 小时前”，超过阈值（预报类 6 小时、流量 12 小时）变为警示色。
- 数据缺失时显示上一次的数据并注明，不显示空白或报错。

## 3. 数据源

六类数据来自四个来源，其中只有流量需要爬取。

| 数据 | 来源 | 获取方式 | 频率 |
| --- | --- | --- | --- |
| 高低潮时间与高度 | [LINZ 潮汐预报](https://www.linz.govt.nz/node/10906)，Lyttelton 年度 CSV | 下载文件后导入，无需账号 | 每年一次 |
| 气温、降雨概率、天气代码、风速、阵风、风向 | [Open-Meteo Forecast API](https://open-meteo.com/en/docs) | HTTP 请求，无需 key | 每 3 小时 |
| 海表水温、浪高、涌浪 | [Open-Meteo Marine API](https://open-meteo.com/en/docs/marine-weather-api) | HTTP 请求，无需 key | 每 3 小时 |
| Waimakariri 流量 | [ECan 站点 66401](https://www.ecan.govt.nz/data/riverflow/sitedetails/66401) | 爬取 | 每 3 小时 |
| 日出日落、月相 | 本地计算（Python `astral` 库） | 无外部请求 | 随采集运行 |

补充约定：

- **潮位曲线**：LINZ 只给高低潮点，连续曲线由相邻高低潮点做余弦插值得到，页面上注明“曲线为估算”。
- **流量爬取**：只取 66401 一个站。优先找页面背后的数据接口，找不到再解析 HTML。每次运行最多请求一次，带缓存，失败沿用上次数据。
- **参考站点**：tides4fishing、swellmap、MSN 天气只作为展示样式的参考，不从它们取数据。
- **时间**：所有来源的时间在采集时统一转成 UTC 存储，页面按 Pacific/Auckland 显示。

## 4. 架构与模块

四个模块各自独立，采集和评分用 Python 跑在 GitHub Actions 上，前端静态部署在 Vercel，记录和数据文件放在 Supabase。

| 模块 | 职责 | 技术 | 运行位置 |
| --- | --- | --- | --- |
| collector | 拉取各数据源，归一化成统一 JSON | Python | GitHub Actions，每小时触发一次，距上次发布不满 170 分钟就跳过，实际约每 3 小时采集一次 |
| scorer | 读取归一化数据和钓点配置，算出每小时分数与推荐时段 | Python | 同一次任务中紧接 collector 运行 |
| web | 展示页面，只读 JSON 和记录表 | Vite + React + TypeScript，ECharts，Leaflet | Vercel |
| records | 钓鱼记录的存储、图片、登录 | Supabase（Postgres、Storage、Auth） | Supabase |

数据流：

1. GitHub Actions 定时触发，collector 拉取数据并输出归一化 JSON。
2. scorer 读取这些 JSON 和 `config/` 下的配置，输出推荐结果。
3. 独立的发布步骤 publish（不含采集和评分逻辑）把两者的输出校验后上传到 Supabase Storage 的公开只读桶；同时把逐小时条件和分数写入 `conditions_hourly` 表，作为历史留存。
4. web 从公开桶读取 JSON，从 Supabase 读取记录，渲染页面。
5. Liang 登录后新增记录，web 把记录写入 Supabase。

这样安排的原因：

- 数据更新不触发 Vercel 重新发布，代码仓库的提交历史也不会被数据提交淹没。
- 采集任务大约每 3 小时写一次 Supabase，免费项目不会因闲置被暂停。
- 采集失败时，桶里仍是上一次的文件，网站照常可用。

仓库结构：

```
collector/        sources/（linz_tides.py、open_meteo.py、ecan_flow.py）、normalize.py、run.py
scorer/           rules/（每条规则一个文件）、engine.py、run.py
publish/          run.py（Schema 校验、上传 Storage、写 conditions_hourly）
config/           spots.yaml、scoring.yaml
schemas/          各 JSON 文件的 JSON Schema
web/              前端
tests/smoke/      数据源冒烟测试
.github/workflows/collect.yml
```

模块边界的硬性要求：

- web 不直接请求任何外部数据源，只读第 5 节定义的文件和记录表。
- collector 不包含任何评分逻辑；scorer 不发任何网络请求，只读写 GitHub Actions 运行环境的临时磁盘上的文件（不是 Liang 的电脑）。上传 Storage 和写数据库只由 publish 步骤完成，publish 是流程步骤，不是第五个模块。
- 每个数据源一个文件，对外只暴露一个返回归一化结构的函数，替换数据源只改这一个文件。

## 5. 数据契约

模块之间只交换下面四个 JSON 文件，结构由 `schemas/` 下的 JSON Schema 定义，采集任务在上传前校验，不通过就不覆盖旧文件。

| 文件 | 产出方 | 内容 |
| --- | --- | --- |
| `conditions/{spot_id}.json` | collector | 该钓点未来 7 天的逐小时条件、高低潮事件、日出日落与月相 |
| `river_flow.json` | collector | 站点 66401 最近 7 天的流量序列 |
| `recommendations.json` | scorer | 每个钓点的逐小时分数、推荐时段、评分理由 |
| `meta.json` | collector | 每个数据源的最近成功时间与状态 |

所有文件的共同约定：

- 顶层带 `schema_version` 和 `generated_at`。
- 时间一律为 UTC 的 ISO 8601 字符串。
- 单位固定并写进字段名：`_m`、`_c`、`_kmh`、`_deg`、`_m3s`。
- 缺失值用 `null`，不省略字段。

`conditions/{spot_id}.json` 的结构示意：

```json
{
  "schema_version": 1,
  "generated_at": "2026-10-08T08:00:00Z",
  "spot_id": "new-brighton-pier",
  "hourly": [
    {
      "time_utc": "2026-10-08T08:00:00Z",
      "tide_height_m": 1.4,
      "tide_phase": "rising",
      "air_temp_c": 11,
      "precip_prob_pct": 2,
      "weather_code": 3,
      "wind_speed_kmh": 14,
      "wind_gust_kmh": 17,
      "wind_dir_deg": 90,
      "wind_relative": "onshore",
      "wave_height_m": 0.8,
      "swell_height_m": 0.6,
      "sea_temp_c": 12.1,
      "is_daylight": false
    }
  ],
  "tide_events": [
    { "time_utc": "2026-10-08T09:10:00Z", "type": "high", "height_m": 2.3 }
  ],
  "days": [
    { "date_local": "2026-10-09", "sunrise_utc": "...", "sunset_utc": "...", "moon_phase": 0.9 }
  ]
}
```

`recommendations.json` 中每个推荐时段包含：`spot_id`、`start_utc`、`end_utc`、`score`（0–100）、`confidence`（`high` 或 `low`）、`reasons`（每条规则的得分和一句说明）、`ruleset_version`。

`recommendations.json` 另含每个钓点的逐小时分数，每项为 `time_utc`、`score`、`vetoed`。

其余契约的结构示意：

- `river_flow.json`：`site_id`、`site_name`、`series`（每项为 `time_utc`、`flow_m3s`）。
- `meta.json`：`sources`，每个数据源一项，含 `status`（`ok` 或 `failed`）、`last_success_utc`、`last_attempt_utc`、`error`（无错误时为 `null`）。
- `conditions_hourly` 表：主键为 `spot_id` 加 `time_utc`；条件列与 `conditions/{spot_id}.json` 的 `hourly` 字段同名；另有 `river_flow_m3s`、`score`、`ruleset_version`、`updated_at`。
- `records` 表：字段见第 8 节，建表 SQL 在 M4 开始时交 Liang 确认。

`is_daylight` 的定义：该小时的起始时刻落在日出前 60 分钟到日落后 60 分钟之间为 `true`，否则为 `false`。

以上都是结构示意。完整的 JSON Schema 和建表 SQL 是 M1 的第一项交付，经 Liang 确认后才成为不可擅改的契约。

## 6. 推荐评分与规则接口

评分以“钓点 × 小时”为单位，每条规则是一个独立的 Python 函数，Liang 新增或修改规则不需要动引擎和前端。

计算方式：

1. 对每个钓点的每个小时，依次运行所有已注册的规则。每条规则返回 0–1 的得分和一句理由。
2. 小时分数 = 各规则得分按权重加权求和，换算到 0–100。
3. 否决规则优先：阵风或浪高超过钓点上限、夜间且该钓点不允许夜钓时，该小时直接记 0 分，并带上安全提示。“夜间”指 is\_daylight 为 false 的小时（定义见第 5 节），所以天光规则加分的日出前、日落后各一小时不会被否决。
4. 把连续高于阈值的小时合并成推荐时段，时段至少 1.5 小时，分数取时段内平均。
5. 距现在 72 小时以内的时段 `confidence` 为 `high`，之后为 `low`。

Liang 影响推荐分数有三个入口，改动量从小到大：

| 入口 | 位置 | 用途 |
| --- | --- | --- |
| 调参数 | `config/scoring.yaml` | 各规则的权重、阈值、时段最短长度 |
| 调钓点 | `config/spots.yaml` | 单个钓点的最佳潮段、风和浪的上限，覆盖全局参数 |
| 写规则 | `scorer/rules/` 下新增一个 Python 文件 | 加入全新的判断逻辑 |

规则的接口约定：

```python
@rule(name="wind", weight_key="wind")
def wind_rule(hour: HourConditions, spot: Spot, ctx: Context) -> RuleResult:
    # hour：该小时的全部条件；spot：钓点配置；ctx：同一钓点前后各小时与流量数据
    return RuleResult(score=0.8, reason="离岸风 12 km/h")
```

- 规则放进 `scorer/rules/` 即自动注册，引擎不需要改。
- 规则可以通过 `ctx` 读取前后几小时的数据和河流流量，用来写“大雨后两天水浑”这类规则。
- 每次修改规则或参数都递增 `ruleset_version`，它会随推荐结果和记录一起保存，便于以后比较不同版本规则的效果。

第一版内置五条简单规则，参数都放在配置里，后续按实际数据调整：

- **潮汐**：距高潮的时间落在钓点配置的最佳区间内得高分。
- **风**：风速越小越好；离岸风加分，向岸风减分。
- **浪**：浪高低于钓点上限得分，越低越高。
- **降雨**：降雨概率越低越好。
- **天光**：日出日落前后各一小时加分。

## 7. 钓点配置

钓点全部定义在 `config/spots.yaml`，新增钓点只需加一段配置，不改代码。第一版两个钓点：

```yaml
- id: new-brighton-pier
  name: New Brighton Pier
  lat: -43.507        # 近似值，待 Liang 确认
  lon: 172.733        # 近似值，待 Liang 确认
  shore_facing_deg: 90      # 岸线朝向，用于判断离岸风或向岸风；待 Liang 确认
  tide_reference: lyttelton
  tide_offset_min: 0        # 相对 Lyttelton 的潮时偏移；待 Liang 填
  allow_night: false        # 待 Liang 确认
  best_tide_window_min: [-120, 120]   # 相对高潮的分钟数
  max_gust_kmh: 45
  max_wave_m: 2.0
  notes: ""                 # Liang 对这个钓点的文字分析，显示在页面上

- id: southshore
  name: Southshore
  lat: -43.558        # 近似值，待 Liang 确认
  lon: 172.752        # 近似值，待 Liang 确认
  shore_facing_deg: null    # 待 Liang 填
  tide_reference: lyttelton
  tide_offset_min: null     # 河口内侧潮时晚于开阔海岸；待 Liang 填

```

上面的阈值都是占位的起始值。标注“待 Liang 填”的字段为 `null` 时，对应规则跳过不计分，并在评分理由里注明。

## 8. 钓鱼记录

每次出钓记一条，包括没钓到的那几次；系统自动附上当时的条件和推荐分数，供以后调规则用。

| 字段 | 填写方式 | 说明 |
| --- | --- | --- |
| 钓点 | 手填，下拉选择 | 来自 `spots.yaml` |
| 开始、结束时间 | 手填 | 可以补记过去的出钓 |
| 结果 | 手填 | 有渔获，或空军 |
| 鱼种、数量、尺寸 | 手填，可空 | 空军时不填 |
| 饵料与钓组 | 手填，可空 |  |
| 备注 | 手填，可空 |  |
| 照片 | 上传 | 存 Supabase Storage，上传前在浏览器端压缩到长边 1600px 以内 |
| 视频 | 贴 YouTube 链接 | 不存视频文件 |
| 条件快照 | 自动 | 出钓时段内的潮位、潮段、风、浪、水温、降雨、流量 |
| 分数快照 | 自动 | 该时段当时的推荐分数和 `ruleset_version` |

自动快照的取数方式：按记录的钓点和时间，从 `conditions_hourly` 历史表里取对应小时的数据。这张表由采集任务每次运行时写入，所以补记几天前的出钓也能取到当时的条件。早于网站上线的出钓没有历史数据，快照留空。历史表存的是预报值，不是实测值：某个小时的条件和分数，是该小时到来前最后一次采集到的预报。

## 9. 权限与合规

所有人可以浏览，只有 Liang 一个账号可以编辑。

- **登录**：Supabase Auth，只建 Liang 一个账号，关闭公开注册。
- **数据库权限**：记录表和图片桶开启行级安全策略，匿名用户只读，登录用户可写。
- **密钥**：前端只使用 Supabase 的匿名公开 key。有写权限的服务 key 只放在 GitHub Actions 的 Secrets 里，不进仓库、不进前端。
- **署名**：页脚列出 LINZ、Open-Meteo、Environment Canterbury，并链接到各自网站，按各自许可要求署名。
- **爬取**：对 ECan 的请求带明确的 User-Agent，两次请求至少间隔 170 分钟，即大约每 3 小时一次。
- **免责说明**：页脚注明“预报仅供参考，出行前请以现场海况为准”。

## 10. 开发顺序

分六个里程碑，按顺序做，每个里程碑由 Liang 确认验收结果后才开始下一个。每个里程碑都写明具体目标、深入分析、实现方案、预期效果、验收标准，并留有开发时填写的验收结果。

### M0 数据源冒烟测试

**具体目标**

在写任何功能之前，用真实请求确认四个数据源都能取到所需数据，并对下面六个未知项逐一给出结论。

**深入分析**

整个设计建立在“数据拿得到”这个前提上，但这些来源在设计阶段都没有实测过。任何一项不成立都会改变 M1 的实现，所以必须最先验证。六个未知项：

1. LINZ 的 CSV 文件格式未知，需要实际下载后确认列结构。
2. LINZ 文件里的时间是否已含夏令时未知。错了会让全站潮时偏一小时，而且不容易被发现。
3. Open-Meteo 的海洋数据在近岸精度有限，两个钓点的坐标可能落在陆地格点上，返回空值。

### M1 采集与数据契约

**具体目标**

collector 每 3 小时自动运行一次，产出第 5 节定义的 `conditions/{spot_id}.json`、`river_flow.json`、`meta.json`，通过 Schema 校验后上传到 Supabase Storage，并把逐小时条件写入 `conditions_hourly` 历史表。

**深入分析**

这一步决定后面所有模块拿到的数据是否可信，难点有六个：

1. **时间统一**：各来源时区不同，新西兰还有夏令时。全部在入口处转成 UTC，之后任何地方不再做时区换算。
2. **潮位曲线**：LINZ 只有高低潮点。相邻两点之间用余弦插值生成逐小时潮位，并推导每小时是涨潮还是落潮。
3. **钓点潮时偏移**：每个钓点在 Lyttelton 基准上加 `tide_offset_min`；该值为空时按 0 处理并在输出里标注。
4. **风相对岸线**：风向是风的来向。来向与岸线朝向的夹角小于 45° 记为向岸，大于 135° 记为离岸，其余为侧风；岸线朝向为空时记为 `null`。
5. **故障隔离**：一个来源失败不能拖垮其他来源。失败的来源沿用上次数据，并在 `meta.json` 里标记失败和最近成功时间。
6. **可重复运行**：同一小时重复运行不能在历史表里产生重复行，写入一律按“钓点 + 时间”做更新或插入。

**实现方案**

- `collector/sources/` 下每个来源一个文件，对外只有一个函数，返回已转成 UTC、单位统一的结构。
- `normalize.py` 把各来源合并到按钓点、按小时的统一网格，计算潮位、潮段、风相对岸线、是否白天。
- 上传前用 `schemas/` 下的 JSON Schema 校验；不通过则不覆盖旧文件，任务标记失败。
- LINZ 文件按年缓存在仓库里；每年 12 月的运行自动下载下一年的文件。
- GitHub Actions 定时任务每小时触发一次；定时触发的运行先检查距上次发布是否已满 170 分钟，不满就跳过，所以实际约每 3 小时采集一次。手动触发的运行不受这个限制。Supabase 的服务 key 放在 Secrets 里。
- 单元测试使用 M0 保存下来的真实返回样本，不在测试里发网络请求。

**预期效果**

- Supabase 的公开桶里始终有最新的三类文件，大约每 3 小时更新一次。
- 历史表逐小时累积，供 M4 的记录快照使用。
- 任何一个来源出问题时，其余数据照常更新，并且能从 `meta.json` 看出是哪个来源出了问题。

### M2 评分引擎与规则

**具体目标**

scorer 读取 M1 的输出和 `config/` 下的配置，产出 `recommendations.json`。Liang 改一个配置数字或新增一个规则文件，就能改变推荐结果，并且能看到每条规则对分数的贡献。

**深入分析**

第一版规则本身很简单，这一步真正要做对的是“以后好改、改了看得懂”：

1. **可解释**：只给一个总分没法调规则。每个推荐时段必须带上每条规则的得分和理由。
2. **可插拔**：规则会越写越多。新增规则不能要求改引擎，否则每次调整都有改坏别处的风险。
3. **纯计算**：scorer 不发网络请求，只读输入文件。这样同一份历史数据可以用不同版本的规则重算，供以后回测。
4. **参数缺失**：钓点的某个参数为空时，对应规则跳过，其余规则的权重重新归一，避免总分被拉低。
5. **安全否决**：阵风或浪高超限时，不管其他条件多好都记 0 分，这类规则优先于加权计算。
6. **版本可追溯**：规则或参数一变，分数的含义就变了。`ruleset_version` 必须随每次改动递增，否则历史分数无法比较。

**实现方案**

- `engine.py`：自动导入 `scorer/rules/` 下所有文件，收集用 `@rule` 注册的函数；按第 6 节的五步计算。
- 五条初版规则各一个文件：潮汐、风、浪、降雨、天光；外加一条否决规则。所有阈值和权重读自 `config/scoring.yaml` 和 `config/spots.yaml`。
- `ruleset_version` 写在 `scoring.yaml` 里手动递增；自动检查在规则文件或配置有改动而版本号未变时报错。
- 提供一个解释命令：输入钓点和时间，打印该小时每条规则的输入、得分、权重和理由。
- scorer 只把结果写成运行环境临时磁盘上的输出文件；publish 步骤把其中的逐小时分数和 `ruleset_version` 写入 `conditions_hourly` 的对应行，供 M4 的分数快照使用。
- 每条规则有单元测试：给定输入，断言得分和理由。

**预期效果**

- 每个钓点未来 7 天都有按分数排序的推荐时段，每个时段附评分理由。
- Liang 调参数只改 YAML，写新规则只加一个 Python 文件。
- 任何一个分数都能用解释命令追溯到具体规则和输入值。

**验收标准**

1. `recommendations.json` 通过 Schema 校验，覆盖两个钓点、未来 7 天。
2. 把 `scoring.yaml` 里某个权重改大后重新运行，相关时段的分数按预期方向变化。
3. 在 `scorer/rules/` 新增一个示例规则文件，不改引擎任何代码，该规则出现在评分理由里。
4. 每个推荐时段的 `reasons` 列出全部参与规则的得分和一句理由。

### M4 钓鱼记录

**具体目标**

Liang 登录后可以新增、编辑、删除钓鱼记录，上传照片、贴视频链接；系统自动为每条记录附上当时的条件快照和分数快照。所有访问者可以浏览记录。

**深入分析**

1. **权限必须在数据库层面生效**：只在界面上隐藏编辑按钮不算权限控制，任何人都可以绕过界面直接调用接口。写入限制必须由 Supabase 的行级安全策略保证。
2. **快照是这个模块的核心价值**：手填的内容随时可以补，但出钓当时的条件过后就取不到了。快照必须在保存时写进记录本身，而不是展示时再去查，这样历史表以后清理或变更都不影响已有记录。
3. **补记**：Liang 不一定当天记录。快照要按记录填写的出钓时间取数，不是按保存时间取数。
4. **一次出钓跨多个小时**：条件快照保存出钓时段内每个小时的数据，不只取一个时间点。
5. **数据缺失**：早于网站上线的出钓，或采集中断期间的出钓，没有历史数据。此时快照留空并在界面上注明，不阻止保存。
6. **图片体积**：手机原图很大，直接上传会很快用完免费存储额度，必须在上传前压缩。

**实现方案**

- Supabase 中建 `records` 表，字段见第 8 节；建 `record-photos` 图片桶。
- 行级安全策略：`records` 表和图片桶匿名只读，登录用户可增删改。关闭公开注册，只保留 Liang 一个账号。
- 登录页使用邮箱加密码；登录后页面出现新增和编辑入口。
- 保存记录时，按钓点和出钓时段从 `conditions_hourly` 读取对应各小时的条件、分数和 `ruleset_version`，写入记录的快照字段。
- 照片在浏览器端压缩到长边 1600px 以内再上传。
- 记录列表按出钓时间倒序，显示结果、鱼种、照片、视频链接和当时条件的摘要。

**预期效果**

- Liang 在手机上一分钟内可以记完一次出钓，包括空军。
- 每条记录都带有当时的潮、风、浪、水温、流量和推荐分数，以后可以直接用来检验和调整规则。
- 朋友能看到记录，但无法修改。

**验收标准**

1. 未登录状态下直接调用 Supabase 接口尝试写入 `records` 和上传图片，均被拒绝。
2. 公开注册已关闭，无法自行创建新账号。

4. 新增一条空军记录，鱼种和数量留空，可以正常保存和显示。
5. 新保存的记录中，条件快照包含出钓时段内每个小时的数据，分数快照包含分数和 `ruleset_version`。
6. 补记一条 2 天前的出钓，快照取到的是 2 天前对应小时的数据，与历史表一致。
7. 记录一条早于历史数据范围的出钓，可以保存，快照为空且界面有说明。
8. 上传一张手机原图，存储中的图片长边不超过 1600px。
9. 编辑和删除记录可用；删除记录时对应的照片文件一并删除。

### M5 收尾与回归

**深入分析**

1. **故障会悄悄发生**：这是个人项目，没有人每天检查。采集停了、某个来源改版了，如果没有通知，可能几周后才被发现，这期间页面展示的是过时数据。

4. **后做的功能可能影响先做的**：M4 改动了数据库和页面，需要确认 M1–M3 的验收项仍然成立。

## 11. 风险与待验证项

下面七项在设计阶段没有实测过，其中前四项由 M0 给出结论。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LINZ 时间是否含夏令时未核实 | 潮时整体偏一小时 | M0 对照当天实际潮时；内部统一存 UTC |
